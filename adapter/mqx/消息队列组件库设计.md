# mqx 消息队列组件库设计

> 实现以代码为唯一真相；本文只描述边界、契约与取舍。

## 一、定位与分层

```
业务 mq / mqlogic          事件定义与处理器
        │
mqx/event                  类型化事件、路由、生命周期、trace
        │
mqx                        最小 SPI + 处理语义 + 契约测试
        │
mqx/impl/{rabbitmqx,kafkax,redisstreamx,memmqx}
```

- `mqx` 只承诺四个后端都能诚实兑现的能力：发布、订阅、确认、关闭。
- 类型化事件与生命周期编排在 `mqx/event`，SPI 不感知。
- 后端拓扑、认证、流控、重连等差异全部留在实现包的 `Config`。

## 二、核心不变量

1. **至少一次 + 幂等**：库只保证 `event_id` 稳定，去重归业务。
2. **处理语义只有一套**：重试、确认、死信由 `mqx.Process` 决定，后端不得各自实现。
3. **确认权默认归框架，接管权归 handler**：返回 nil 就 Ack，handler 显式 Ack/Nack 后框架不再干预。
4. **耗尽后必须有落点**：死信或显式丢弃二选一，配置校验拒绝「既没 DLQ、又没声明可丢」。
5. **生命周期可观测**：订阅有 `Err()`、关闭有截止时间、永久断连必须上报。
6. **库不碰序列化，也不替业务决定发布失败怎么办**。

## 三、核心契约

```go
type Broker interface {
    Publisher() (Publisher, error)
    Subscriber() (Subscriber, error)
    Ping(ctx context.Context) error
    Close(ctx context.Context) error // 先停订阅，再关连接
}

type Publisher interface {
    Publish(ctx context.Context, msg *Message) (*PublishResult, error)
}
type BatchPublisher interface { // 可选能力
    PublishBatch(ctx context.Context, msgs []*Message) ([]PublishResult, error)
}

type Subscriber interface {
    Subscribe(ctx context.Context, spec SubscriptionSpec, handler Handler) (Subscription, error)
}
type Subscription interface {
    Err() <-chan error       // 只发致命错误；结束即关闭
    Close(ctx context.Context) error
}
type Handler func(ctx context.Context, d *Delivery) error
```

消息是纯数据，确认能力在 `Delivery` 上：

```go
type Message struct {
    ID, Destination, RoutingKey, Key string
    Headers map[string]string
    Body []byte
    Timestamp time.Time
}

type Delivery struct {
    Message
    Partition int32; Offset int64
    Redelivered bool; Attempt int
}
func (d *Delivery) Ack() error
func (d *Delivery) Nack(requeue bool) error
func (d *Delivery) Settled() bool
```

`Nack(requeue=true)` 的语义是**尽力重投**：Rabbit 立即 requeue，Redis 重新 XADD，Kafka 只能复制重投或等重平衡。`Concurrency` 是并行度上限，实际并行度可能被后端压低（Kafka 受 partition 数限制）。

## 四、处理语义

| handler 结果 | 行为 |
|---|---|
| `nil` | Ack |
| 普通 error | 按 `RetryPolicy` 进程内重试；耗尽后按 `OnExhausted` |
| `Permanent(err)` | 不重试，直接死信 |
| `RetryAfter(err, d)` | 用 d 覆盖本次退避时长 |
| panic | 转为 `Permanent`（附堆栈），不重试 |
| handler 调过 `Ack/Nack` | 框架不再干预（`Settled()`） |
| ctx 取消 | 不确认，交给 broker 重投；等待在途处理退出 |

`Process` 是唯一实现，适配器只负责投递与底层确认。

发布侧错误分级：权限不足、exchange 类型不匹配、消息过大等永久性 broker 错误由适配器的 `ClassifyPublishError` 用 `Permanent` 包装；连接/确认失败返回 `ErrUnavailable`，调用方可重试。

## 五、订阅规格

```go
type SubscriptionSpec struct {
    Destination, BindingKey, Group string
    Concurrency   int
    MaxInFlight   int
    HandlerTimeout time.Duration
    Retry         RetryPolicy
    DeadLetter    DeadLetterPolicy
    OnExhausted   ExhaustedAction // DeadLetter | Discard
}

type RetryPolicy struct {
    MaxAttempts  int
    InitialDelay time.Duration
    MaxDelay     time.Duration
    MaxElapsed   time.Duration
    Jitter       float64
}

type DeadLetterPolicy struct {
    Enabled     bool
    Destination string // 死信目的地
    RoutingKey  string // 空则沿用原 routing key
    IncludeMeta bool
}
```

- 零值 `RetryPolicy{}` = 仅处理 1 次。
- `OnExhausted` 零值为 `ExhaustedDeadLetter`，此时必须配置死信目的地；想丢弃必须显式声明 `ExhaustedDiscard`。
- 死信目的地不得与主目的地相同，避免消息在两者之间循环。
- 配置错误在 `Subscribe` 时返回 `ErrInvalidSpec`，不等到第一条消息。

## 六、后端语义矩阵

| 能力 | RabbitMQ | Kafka | Redis Stream | 内存 |
|---|---|---|---|---|
| Destination | exchange | topic | stream | 内存 topic |
| RoutingKey | routing key | `mqx.event_type` header | 字段 `rk` | header |
| BindingKey | 服务端绑定 | 客户端过滤 | 客户端过滤 | 客户端过滤 |
| Group | queue | consumer group | consumer group | 同组分摊 |
| Concurrency | N 条消费 channel | 组内 N 个 client，受 partition 数限制 | 组内 N 个 consumer | N 个 worker |
| MaxInFlight | 每 channel qos × N | 建议值，受 fetch 配置约束 | 队列缓冲上限 | 队列上限 |
| Ack | `basic.ack` | commit offset | `XACK` | 出队 |
| Nack(false) | `basic.nack(false,false)` | commit | `XACK` | 丢弃 |
| Nack(true) | 立即 requeue | 复制重投 | 重新 XADD | 立即重投 |
| 死信 | 应用级发布 + 预声明 DLQ 队列 | 应用级发布 | 重新 XADD | 应用级发布 |

Rabbit 单条发布使用 `mandatory=true` 并检查 `basic.return`：exchange 没有匹配队列时返回 `ErrUnavailable`，不得视为发布成功。批量发布不检测 unroutable，需要该保证时逐条发布。

死信写入失败时**不得确认原消息**：

- Rabbit：停止订阅、不确认，channel 关闭后由 broker 重投；避免无限 requeue 热循环；
- Kafka：停止订阅、不提交 offset，避免后续提交越过该消息；
- Redis：留在 PEL，由 `ClaimIdle` 触发的 `XAUTOCLAIM` 回收。

## 七、事件层

```go
spec := event.NewEventSpec[UserCreated]("user.events", "user.created",
    event.WithVersion("v1"), event.WithProducer("user-svc"))

result, err := spec.Publish(ctx, publisher, &UserCreated{ID: 1})

router, _ := runtime.NewRouter()
event.HandleEvent(router, spec, func(ctx context.Context, e *UserCreated) error {
    id := event.EventIDFrom(ctx) // 幂等键
    return nil
})
runtime.Start(router, spec.SubscriptionSpec{...})
```

消息头信封（事件层写入，适配器只透传）：

| 头 | 含义 |
|---|---|
| `mqx.event_id` | 稳定唯一标识，与 `Message.ID` 同值 |
| `mqx.event_type` | 事件类型，与 `RoutingKey` 同值 |
| `mqx.schema_version` | 负载契约版本 |
| `mqx.occurred_at` | 事件发生时间（RFC3339Nano） |
| `mqx.producer` | 生产者标识 |

死信额外携带 `mqx.original_destination`、`mqx.original_routing_key`、`mqx.original_group`、`mqx.attempts`、`mqx.error`、`mqx.failed_at`。

Router 的规则：

- 未知 routing key：记录一次并 Ack，向前兼容新增事件类型。
- 解码失败：返回 `Permanent`，按死信策略投递。
- 事件定义留在业务侧，不进公共库。

## 八、可观测性与生命周期

- 日志统一 `slog`；核心不依赖具体日志框架。
- `mqx.Metrics` 暴露发布、消费、订阅停止三类事件，由调用方接入 Prometheus。
- `event` 层在发布与消费两侧注入 trace context，并在头中传播 W3C `traceparent`。
- `Runtime.Close(ctx)`：停止接受新消息 → 等待在途 handler → 关闭订阅 → 关闭 Broker；超时返回 `ctx.Err()`。
- 永久断连通过 `Subscription.Err()` 上报，不允许静默退出。

## 九、测试

- `mqtest` 是由 `_test.go` 组成的契约测试包：同一组用例对 mem / RabbitMQ / Kafka / Redis Stream 运行，覆盖发布订阅、routing 过滤、消费组分摊、手动确认/拒绝、重试、永久失败、死信、panic、handler 超时、优雅关闭、批量发布，以及发布错误分类。
- `memmqx` 是完整的内存实现（同组分摊、重投、死信），默认在 CI 跑。
- RabbitMQ / Kafka / Redis Stream 用 `-tags integration` + 环境变量开启；缺环境变量时 `t.Skip`，连不上时 `t.Fatalf`。

## 十、非目标

恰好一次、全局顺序、跨 broker 事务、DLQ 重放 UI，以及让四个后端在重投时机上完全一致。差异写入矩阵，不假装一致。
